Threads Analytics is a Next.js app with a PostgreSQL database. On a server you manage, Docker Compose is the quickest way to run it: one file starts the app and its database together. You can also run the prebuilt Docker image against a database you already have, build it from source, or run it on Vercel with a cron job doing the syncing. This guide covers what each route needs, how to keep your posts syncing, and how to update.

If you’d rather not set this up by hand, the [one-click template and agent prompts](/#deploy) for Railway and Vercel do it all for you.

## What you need

- **A PostgreSQL database.** A managed service or one on your own server; the app only needs its connection string. Docker Compose brings its own.
- **Somewhere to run the app.** A server that runs Docker images (amd64 or arm64), Vercel, or any machine with Node.js 22.12+ or 24+.
- **A Threads access token.** You add it in the dashboard after deploying. The [token guide](/token-guide) walks through getting one.

## Environment variables

Set these wherever the app runs: an env file for Docker, the project settings on Vercel, or `.env.local` when running from source.

<Table variant="text">

| Variable                 | Required | What it’s for                                                                                            |
| ------------------------ | -------- | -------------------------------------------------------------------------------------------------------- |
| `APP_PASSWORD`           | Yes      | The password you sign in to the dashboard with.                                                          |
| `DATABASE_URL`           | Yes      | The PostgreSQL connection string.                                                                        |
| `TOKEN_ENCRYPTION_KEY`   | Yes      | Encrypts the Threads access tokens stored in the database. Generate one with `openssl rand -hex 32`.     |
| `SYNC_SCHEDULER_ENABLED` | No       | `true` starts the built-in sync scheduler. Set it on Docker, a VPS or Railway; leave it unset on Vercel. |
| `CRON_SECRET`            | No       | Protects `/api/cron/sync`, the endpoint a cron job calls to sync. Required on Vercel.                    |

</Table>

A complete env file for Docker or a VPS looks like this:

```dotenv
APP_PASSWORD=choose-a-long-password
DATABASE_URL=postgresql://user:password@your-db-host:5432/threads_analytics
TOKEN_ENCRYPTION_KEY=paste-the-output-of-openssl-rand-hex-32
SYNC_SCHEDULER_ENABLED=true
```

<Callout>Keep `TOKEN_ENCRYPTION_KEY` the same for as long as the deployment lives. Stored tokens can only be decrypted with the key that encrypted them, so changing it means pasting every account’s token again. Your synced posts and history are not affected.</Callout>

## Docker Compose

The repository’s [`docker-compose.yml`](https://github.com/ridemountainpig/threads-analytics/blob/main/docker-compose.yml) runs the dashboard next to its own PostgreSQL, so there is no database to set up first. In an empty folder on your server, download it and write a `.env` file beside it:

```bash
curl -fsSLO https://raw.githubusercontent.com/ridemountainpig/threads-analytics/main/docker-compose.yml
cat > .env <<EOF
APP_PASSWORD=choose-a-long-password
TOKEN_ENCRYPTION_KEY=$(openssl rand -hex 32)
POSTGRES_PASSWORD=$(openssl rand -hex 16)
EOF
docker compose up -d
```

Swap in your own `APP_PASSWORD` before running it. Compose waits for the database, applies migrations, and serves the dashboard on port 3000 with the sync scheduler already on, so you don’t set `DATABASE_URL` or `SYNC_SCHEDULER_ENABLED` yourself. Any other variable in `.env`, such as `CRON_SECRET`, is passed to the app as well.

Your posts and accounts live in the `postgres-data` volume, which survives restarts and updates. `docker compose logs -f app` follows the server log.

<Callout>PostgreSQL reads `POSTGRES_PASSWORD` only when it first creates the volume, so keep the value you started with. `docker compose down -v` deletes the volume, and every synced post with it.</Callout>

## Docker

To run only the app container against a PostgreSQL you already have, use the image on [GitHub Container Registry](https://github.com/ridemountainpig/threads-analytics/pkgs/container/threads-analytics), published for amd64 and arm64. With the variables in `.env.local`, start it with:

```bash
docker run -d --name threads-analytics --restart unless-stopped \
  -p 3000:3000 --env-file .env.local \
  ghcr.io/ridemountainpig/threads-analytics:latest
```

Each time the container starts, it applies any pending database migrations, then serves the dashboard on port 3000. Put a reverse proxy in front of it for HTTPS.

<Callout>Inside the container, `localhost` means the container itself. If PostgreSQL runs on the same machine, point `DATABASE_URL` at an address the container can reach, such as a database container on the same Docker network.</Callout>

To build the image yourself instead, run this from a clone of the repository:

```bash
docker build -t threads-analytics .
docker run -d --name threads-analytics --restart unless-stopped \
  -p 3000:3000 --env-file .env.local threads-analytics
```

## Run from source

You need Node.js 22.12+ or 24+ and pnpm.

```bash
git clone https://github.com/ridemountainpig/threads-analytics.git
cd threads-analytics
pnpm install
pnpm prisma:generate
cp .env.example .env.local  # then fill in the variables
pnpm build
pnpm start
```

`pnpm start` applies pending migrations, then starts the server on port 3000. Keep it running with a process manager such as systemd or pm2.

## Vercel

Vercel can’t keep a process running between requests, so the built-in scheduler never runs there. Syncing goes through a Vercel Cron Job that calls `/api/cron/sync` instead.

The [Vercel Agent guide](/deploy/vercel-agent) deploys the prebuilt image through Vercel MCP and sets up the Neon database, the variables and this cron job for you. To add the cron job yourself, put a `vercel.json` in the project root:

```json
{
  "crons": [{ "path": "/api/cron/sync", "schedule": "0 0 * * *" }]
}
```

Then add `CRON_SECRET` to the project’s environment variables. Vercel sends it as `Authorization: Bearer <CRON_SECRET>` with every cron request, and the endpoint rejects requests without it.

The Hobby plan runs cron jobs at most once a day, so keep the daily schedule there. On a paid plan you can run it as often as the sync interval you choose in Settings.

## Keep posts syncing

Automatic syncing stays off until you choose an interval. After deploying, open **Settings → Auto Sync** in the dashboard and pick how often to sync: every hour, every 6 hours, daily, or a custom number of minutes. Each run syncs every connected account, not just the one you’re viewing.

What triggers the sync depends on where the app runs:

- **Docker, a VPS or Railway:** set `SYNC_SCHEDULER_ENABLED=true` (Docker Compose already does). The scheduler starts with the server and regularly checks which accounts are due.
- **Vercel:** the cron job above.
- **Anywhere else:** any scheduler can call the endpoint with your `CRON_SECRET`.

```bash
curl -fsS -H "Authorization: Bearer $CRON_SECRET" https://analytics.example.com/api/cron/sync
```

Calling it more often than your interval is harmless: accounts that aren’t due yet are skipped.

## Updating

New versions ship as a new Docker image, and migrations run automatically when the app starts, so updating only means getting the new image or code. Your posts, insights and accounts stay in the database.

With Docker Compose, run these in the folder that holds `docker-compose.yml`:

```bash
docker compose pull
docker compose up -d
```

On plain Docker, pull the new image and recreate the container with the same flags:

```bash
docker pull ghcr.io/ridemountainpig/threads-analytics:latest
docker rm -f threads-analytics
docker run -d --name threads-analytics --restart unless-stopped \
  -p 3000:3000 --env-file .env.local \
  ghcr.io/ridemountainpig/threads-analytics:latest
```

- **From source:** run `git pull`, then `pnpm install`, `pnpm prisma:generate` and `pnpm build`, and restart `pnpm start`.
- **Railway:** redeploy the service from the Railway dashboard.
- **Vercel:** redeploy the project.

## After deploying

1. Open the app and sign in with your `APP_PASSWORD`.
2. Go to **Settings → Add Threads account** and paste your access token. The first sync starts right away and can take a few minutes.
3. Choose a sync interval under **Settings → Auto Sync**.

To ask Claude or another AI agent about your data, connect it to the built-in [MCP server](/mcp) at `/api/mcp`.
